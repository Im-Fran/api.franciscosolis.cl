## Repo purpose

`cms` is the content management Worker for the `api.franciscosolis.cl` monorepo. Like
`landing` and `auth`, it is not public: the root gateway (`apps/api`) reaches it through
the `CMS` service binding and proxies `/cms/*` to it, so its public base URL is
`https://api.franciscosolis.cl/cms`. It lives at `apps/cms`.

It owns three things:

- **Landing page content** — projects, experience, skills, certifications, education, in
  one `content_entries` table discriminated by collection.
- **Legal pages** — privacy policy, terms and friends, as versioned documents.
- **Outgoing email** — ad-hoc or templated, sent through Cloudflare Email Sending from the
  `mail.franciscosolis.cl` domain.

Reads of published content are public (that is what the website calls); everything under
`/admin` requires an access token from `apps/auth` belonging to an `@franciscosolis.cl`
account.

## Stack

- Cloudflare Workers, Hono 4, hono-openapi + valibot, Wrangler 4, TypeScript strict.
- **Drizzle ORM** over D1 (`drizzle-orm/d1`), backed by the `franciscosolis_cms` database.
- **`@franciscosolis/emails`** (workspace package) for the house layout outgoing mail is wrapped in.
- Dependency versions come from the parent workspace's pnpm `catalog` — use `catalog:`,
  never a hardcoded version.
- `pnpm` install/deps are managed from the **monorepo root**.

## Commands (run from this directory, `apps/cms/`)

- `pnpm run dev` → `wrangler dev --ip 0.0.0.0 --port 8790 --inspector-port 9232`
- `pnpm run deploy` → `wrangler deploy --minify`
- `pnpm run cf-typegen` → run after editing `wrangler.jsonc` bindings.
- `pnpm run db:generate` → `drizzle-kit generate`, writes a new SQL migration.
- `pnpm run db:migrate:local` / `pnpm run db:migrate:remote` → apply migrations with Wrangler.

## Environment

This Worker has **no secrets**. It verifies access tokens against the auth Worker's public
JWKS, so there is no signing key and no client secret to hold. `.dev.vars` (gitignored, copy
from `.dev.vars.example`) only overrides `AUTH_ISSUER` so a local CMS trusts the local auth
Worker; the keys themselves arrive over the `AUTH` service binding. Everything else lives in
`wrangler.jsonc` under `vars`.

## Source layout

- `src/index.ts` — Hono app: charset/cache middleware, `onError`, `GET /`, route mounting,
  `/openapi.json`.
- `src/db/schema.ts` — the entire D1 schema. `src/db/client.ts` builds a per-request client.
- `src/lib/` — `collections.ts` (the content model registry), `locales.ts` (the published
  languages and the translation-override rules), `jwks.ts` (offline token verification),
  `config.ts` (statuses, limits, TTLs), `validation.ts` (shared valibot fragments),
  `errors.ts` (unique-violation → 409), `slug.ts`, `template.ts`.
- `src/middleware/auth.ts` — `requireEditor`, the access gate.
- `src/services/` — `content.ts`, `legal.ts`, `email.ts` (sender allowlist, send + log),
  `audit.ts`.
- `src/routes/` — `content.ts` and `legal.ts` are the public reads; `routes/admin/` is the
  editorial API.
- `migrations/` — `0000_init.sql` and `0002_content_translations.sql`, generated by
  drizzle-kit; `0001_seed_landing_content.sql` and `0003_seed_spanish_translations.sql`,
  hand-written (see below). Wrangler applies them in **filename order**, which is why the
  DDL adding `translations` sorts before the seed that fills it. `drizzle-kit generate`
  numbers from the journal, which the hand-written seeds are absent from, so it emits a
  prefix that collides with one of them — rename the emitted file (and its `tag` in
  `migrations/meta/_journal.json`) to the next free number.

## Architecture notes (non-obvious)

- **Adding a content collection is a registry entry, not a migration.** Every collection
  lives in `content_entries`, discriminated by `collection`; the fields specific to one
  collection go in the `data` JSON blob, whose shape is a valibot schema in
  `src/lib/collections.ts`. Adding `talks` means adding one entry to `COLLECTIONS` — the
  routes, the listing and the OpenAPI doc pick it up automatically.
- **Those `data` schemas are `strictObject` on purpose**: an unknown key is a 422, not a
  silently stored typo. `data` is replaced wholesale on PATCH, never merged.
- **Tokens are verified offline; the key set comes over the `AUTH` service binding.**
  `lib/jwks.ts` reads the published JWKS and caches it per isolate for an hour. A `kid`
  that is not in the cached set forces one refetch before failing, which is what a key
  rotation looks like from here — without it, a rotation would break sign-in for up to an
  hour. The binding is not optional: this Worker sits behind `api.franciscosolis.cl`, and a
  Worker's subrequest to its own zone skips Workers routing and goes to the zone's origin,
  which does not exist — the public JWKS URL answered `522` from in here, so the gate
  refused *every* token. The suite pins this by making global `fetch` throw.
- **The trade-off that buys**: `roles`/`permissions` on the token are a snapshot, so a
  revoked role lingers for at most the access-token lifetime (15 minutes). The
  email-domain check in `requireEditor` is the actual access rule, and it is evaluated on
  every request.
- **Three things must hold to get in** (`requireEditor`): a valid unexpired signature from
  the auth issuer, an `aud` in `CMS_ALLOWED_AUDIENCES` (a token minted for the public
  website is not a CMS token), and a *verified* email whose domain is in
  `CMS_ALLOWED_EMAIL_DOMAINS`. Domain matching is on the full domain label, never a suffix,
  so `notfranciscosolis.cl` cannot slip through.
- **Token errors are redacted before they are returned** (`describeTokenError`): several
  `hono/jwt` errors embed the offending token in their message, which would echo a live
  credential into a response body and any log that captures it.
- **5xx bodies are generic** (`onError`): an unexpected error here is usually a Drizzle
  failure whose message carries the full statement plus bound parameters — including email
  bodies and recipients. It is logged, never returned.
- **Unique-violation detection has to walk the `cause` chain** (`lib/errors.ts`): Drizzle
  wraps the D1 error, so matching on the top-level message alone never fires and a
  duplicate slug 500s instead of 409-ing. Use `asConflict` for any new unique index.
- **Public routes only ever see `published`**, and say 404 for anything else: the existence
  of a draft is not public information. They are also the only responses with a `public`
  Cache-Control; the global middleware defaults everything else to `no-store`.
- **`published_at` is stamped once**, the first time an entry or page goes live, and kept
  through later unpublish/republish cycles — it records when the thing was announced, not
  when it was last toggled.
- **Emails are bounded on every side**: only an authenticated editor can send, the sender
  must be in `MAIL_ALLOWED_SENDERS` *and* in `allowed_sender_addresses` (wrangler.jsonc,
  the real boundary Cloudflare enforces), recipients are capped, and every attempt is
  written to `email_messages` before it is tried and updated with the outcome.
- **A provider failure is a 202 with `status: "failed"`**, not an HTTP error: the attempt
  was recorded either way, and the caller needs the message id to find it.
- **Outgoing mail is wrapped in the shared house layout by default** (`applyBrandedLayout` in
  `services/email.ts`, `ContentEmail` in `@franciscosolis/emails`), so an editorial send and a
  sign-in link from `apps/auth` arrive looking like the same sender. Three rules hold it in
  place: `layout: "raw"` opts out for a body that is already a complete document; a message with
  no HTML part is never promoted to one, because that is a change of intent rather than of
  styling; and an editor-supplied `text` always wins, with the derived plain-text alternative
  only filling the gap for an HTML-only message that used to go out with no text part at all.
  What is logged in `email_messages` is the *wrapped* body — the log has to be what was sent.
- **Prettier is aliased out of the bundle** (`alias` in `wrangler.jsonc`, mirrored in
  `vitest.config.ts`): `@react-email/render` imports it statically for a `pretty: true` option
  this Worker never uses, and it is ~1.5 MB of formatter parsed on every cold start. The stub
  (`packages/emails/src/prettier-stub.ts`) throws if it is ever actually called.
- **Template variables are derived from the text**, never declared by hand, so the stored
  list cannot drift from the `{{ placeholders }}` actually used. A send missing any of them
  is refused rather than mailing "Hola ,".
- **The template renderer is intentionally not a template engine** (`lib/template.ts`): no
  conditionals, no loops, no expression evaluation. It runs inside a Worker that can send
  mail from a real domain.
- **The landing page's content is seeded by a migration, not by an editor.**
  `0001_seed_landing_content.sql` carries the copy franciscosolis.cl already renders — the
  projects, the work timeline, the toolbox, the certifications, the degree and the two legal
  documents. It is hand-written and, like the auth Worker's `0001_seed.sql`, deliberately absent
  from `migrations/meta/_journal.json`: it contains no DDL, so drizzle's snapshot stays an accurate
  picture of the schema. Keep it that way — a `CREATE`/`ALTER` in there desynchronises the snapshot
  silently, and `test/functional/seed-content.test.ts` fails the run if one appears. Two more
  things hold: every insert is an `INSERT OR IGNORE` keyed on the unique indexes, so re-applying it
  writes nothing and never clobbers an entry an editor has rewritten; and the values are what the
  admin API would have accepted, because nothing validates a raw INSERT and a `data` blob with a
  misspelled key is an entry the CMS can open but never save (`PATCH` replaces `data` wholesale
  and validates it). The same test parses every seeded blob through `parseCollectionData` for
  exactly that reason.
- **The Spanish copy is seeded the same way**, by `0003_seed_spanish_translations.sql`, lifted from
  the site's own `src/translations/es/` namespaces. Every statement there is an `UPDATE … WHERE
  translations = '{}'` rather than an unconditional one: that is what makes re-applying it a no-op
  *and* keeps it from silently reverting a translation an editor has since rewritten in the CMS.
  `skills` is deliberately only translated where the Spanish name actually differs — an override
  repeating the English product name verbatim is a row that can only ever go stale.
- **The site is bilingual, and a translation is an override map rather than a second row.**
  Both `content_entries` and `legal_pages` carry a `translations` column holding
  `{"es":{"title":"…"}}`; the row itself *is* the default locale (`en`). Every public read takes
  `?locale`, resolves the overrides server-side and answers with plain `title`/`body` fields plus
  a `locale` saying which language actually came back and an `available_locales` a language
  switcher is built from. Five things follow, and `src/lib/locales.ts` is where they live:
  a field nobody translated falls back to the row rather than rendering empty, so a
  half-translated entry still renders; a locale with nothing behind it is dropped on write, so
  `available_locales` never advertises a language that is only fallback; the default locale is
  *not* a valid key in the map, because a second home for the English title is a question about
  which one wins; `?locale` is a query parameter and not `Accept-Language` precisely because
  these responses are publicly cacheable and a header-chosen language needs a `Vary` somebody
  will eventually forget; and the admin routes always answer in the default locale with the raw
  map beside it, because a localized `title` in an editorial response is an editor saving the
  Spanish back over the English row. `translations` is replaced wholesale on PATCH, exactly like
  `data`.
- **Only prose is translated, never structure.** The override map covers `title`, `subtitle`,
  `summary` and `body` (and `title`/`summary`/`body` on a legal page) — the fields a visitor
  reads. Slugs, ordering, dates, links, tags and the `data` blob are the same fact in every
  language, and duplicating them per locale is how a reorder ends up applied to one language's
  list and not the other's.
- **The CMS client application must exist in the auth database** with the id listed in
  `CMS_ALLOWED_AUDIENCES` — see `apps/auth/migrations/0002_cms_application.sql`. Its
  redirect URIs are placeholders until the CMS front-end has a real URL.
