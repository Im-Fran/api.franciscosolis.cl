## Repo purpose

`cms` is the content management Worker for the `api.franciscosolis.cl` monorepo. Like
`landing` and `auth`, it is not public: the root gateway (`apps/api`) reaches it through
the `CMS` service binding and proxies `/cms/*` to it, so its public base URL is
`https://api.franciscosolis.cl/cms`. It lives at `apps/cms`.

It owns three things:

- **Landing page content** — projects, experience, skills, certifications, education, in
  one `content_entries` table discriminated by collection.
- **Legal pages** — privacy policy, terms and friends, as versioned documents.
- **Outgoing email** — ad-hoc or templated, sent through Cloudflare Email Sending from the
  `mail.franciscosolis.cl` domain.

Reads of published content are public (that is what the website calls); everything under
`/admin` requires an access token from `apps/auth` belonging to an `@franciscosolis.cl`
account.

## Stack

- Cloudflare Workers, Hono 4, hono-openapi + valibot, Wrangler 4, TypeScript strict.
- **Drizzle ORM** over D1 (`drizzle-orm/d1`), backed by the `franciscosolis_cms` database.
- Dependency versions come from the parent workspace's pnpm `catalog` — use `catalog:`,
  never a hardcoded version.
- `pnpm` install/deps are managed from the **monorepo root**.

## Commands (run from this directory, `apps/cms/`)

- `pnpm run dev` → `wrangler dev --ip 0.0.0.0 --port 8790 --inspector-port 9232`
- `pnpm run deploy` → `wrangler deploy --minify`
- `pnpm run cf-typegen` → run after editing `wrangler.jsonc` bindings.
- `pnpm run db:generate` → `drizzle-kit generate`, writes a new SQL migration.
- `pnpm run db:migrate:local` / `pnpm run db:migrate:remote` → apply migrations with Wrangler.

## Environment

This Worker has **no secrets**. It verifies access tokens against the auth Worker's public
JWKS, so there is no signing key and no client secret to hold. `.dev.vars` (gitignored, copy
from `.dev.vars.example`) only overrides `AUTH_JWKS_URL` / `AUTH_ISSUER` so a local CMS
trusts the local auth Worker. Everything else lives in `wrangler.jsonc` under `vars`.

## Source layout

- `src/index.ts` — Hono app: charset/cache middleware, `onError`, `GET /`, route mounting,
  `/openapi.json`.
- `src/db/schema.ts` — the entire D1 schema. `src/db/client.ts` builds a per-request client.
- `src/lib/` — `collections.ts` (the content model registry), `jwks.ts` (offline token
  verification), `config.ts` (statuses, limits, TTLs), `validation.ts` (shared valibot
  fragments), `errors.ts` (unique-violation → 409), `slug.ts`, `template.ts`.
- `src/middleware/auth.ts` — `requireEditor`, the access gate.
- `src/services/` — `content.ts`, `legal.ts`, `email.ts` (sender allowlist, send + log),
  `audit.ts`.
- `src/routes/` — `content.ts` and `legal.ts` are the public reads; `routes/admin/` is the
  editorial API.
- `migrations/` — `0000_init.sql`, generated by drizzle-kit.

## Architecture notes (non-obvious)

- **Adding a content collection is a registry entry, not a migration.** Every collection
  lives in `content_entries`, discriminated by `collection`; the fields specific to one
  collection go in the `data` JSON blob, whose shape is a valibot schema in
  `src/lib/collections.ts`. Adding `talks` means adding one entry to `COLLECTIONS` — the
  routes, the listing and the OpenAPI doc pick it up automatically.
- **Those `data` schemas are `strictObject` on purpose**: an unknown key is a 422, not a
  silently stored typo. `data` is replaced wholesale on PATCH, never merged.
- **Tokens are verified offline, and there is deliberately no binding back into `auth`.**
  `lib/jwks.ts` fetches the published JWKS and caches it per isolate for an hour. A `kid`
  that is not in the cached set forces one refetch before failing, which is what a key
  rotation looks like from here — without it, a rotation would break sign-in for up to an
  hour.
- **The trade-off that buys**: `roles`/`permissions` on the token are a snapshot, so a
  revoked role lingers for at most the access-token lifetime (15 minutes). The
  email-domain check in `requireEditor` is the actual access rule, and it is evaluated on
  every request.
- **Three things must hold to get in** (`requireEditor`): a valid unexpired signature from
  the auth issuer, an `aud` in `CMS_ALLOWED_AUDIENCES` (a token minted for the public
  website is not a CMS token), and a *verified* email whose domain is in
  `CMS_ALLOWED_EMAIL_DOMAINS`. Domain matching is on the full domain label, never a suffix,
  so `notfranciscosolis.cl` cannot slip through.
- **Token errors are redacted before they are returned** (`describeTokenError`): several
  `hono/jwt` errors embed the offending token in their message, which would echo a live
  credential into a response body and any log that captures it.
- **5xx bodies are generic** (`onError`): an unexpected error here is usually a Drizzle
  failure whose message carries the full statement plus bound parameters — including email
  bodies and recipients. It is logged, never returned.
- **Unique-violation detection has to walk the `cause` chain** (`lib/errors.ts`): Drizzle
  wraps the D1 error, so matching on the top-level message alone never fires and a
  duplicate slug 500s instead of 409-ing. Use `asConflict` for any new unique index.
- **Public routes only ever see `published`**, and say 404 for anything else: the existence
  of a draft is not public information. They are also the only responses with a `public`
  Cache-Control; the global middleware defaults everything else to `no-store`.
- **`published_at` is stamped once**, the first time an entry or page goes live, and kept
  through later unpublish/republish cycles — it records when the thing was announced, not
  when it was last toggled.
- **Emails are bounded on every side**: only an authenticated editor can send, the sender
  must be in `MAIL_ALLOWED_SENDERS` *and* in `allowed_sender_addresses` (wrangler.jsonc,
  the real boundary Cloudflare enforces), recipients are capped, and every attempt is
  written to `email_messages` before it is tried and updated with the outcome.
- **A provider failure is a 202 with `status: "failed"`**, not an HTTP error: the attempt
  was recorded either way, and the caller needs the message id to find it.
- **Template variables are derived from the text**, never declared by hand, so the stored
  list cannot drift from the `{{ placeholders }}` actually used. A send missing any of them
  is refused rather than mailing "Hola ,".
- **The template renderer is intentionally not a template engine** (`lib/template.ts`): no
  conditionals, no loops, no expression evaluation. It runs inside a Worker that can send
  mail from a real domain.
- **`D1` needs its real `database_id`**: `wrangler.jsonc` ships a placeholder. Run
  `wrangler d1 create franciscosolis_cms` and paste the id in, or remote deploys will fail
  to bind the database.
- **The CMS client application must exist in the auth database** with the id listed in
  `CMS_ALLOWED_AUDIENCES` — see `apps/auth/migrations/0002_cms_application.sql`. Its
  redirect URIs are placeholders until the CMS front-end has a real URL.
