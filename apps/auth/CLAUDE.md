## Repo purpose

`auth` is the centralized authentication Worker for the `api.franciscosolis.cl` monorepo.
Like `landing`, it is not public: the root gateway (`apps/api`) reaches it through the
`AUTH` service binding and proxies `/auth/*` to it, so its public base URL is
`https://api.franciscosolis.cl/auth`. It lives at `apps/auth`.

It implements a full **OAuth 2.0 + OpenID Connect provider** on top of two authentication
providers (magic link, Google), backed by the `franciscosolis_auth` D1 database, and issues
**EdDSA-signed JWT access tokens** any other service can verify offline against its JWKS.
Confidential clients authenticate with rotatable client secrets, and relying parties that speak
plain OIDC — another application on its own domain, or Cloudflare Access — can use it unchanged.

## Stack

- Cloudflare Workers, Hono 4, hono-openapi + valibot, axios, Wrangler 4, TypeScript strict.
- **Drizzle ORM** over D1 (`drizzle-orm/d1`).
- **`@franciscosolis/emails`** (workspace package) for the magic link and invitation bodies.
- Dependency versions come from the parent workspace's pnpm `catalog` — use `catalog:`,
  never a hardcoded version.
- `pnpm` install/deps are managed from the **monorepo root**.

## Commands (run from this directory, `apps/auth/`)

- `pnpm run dev` → `wrangler dev --ip 0.0.0.0 --port 8789 --inspector-port 9231`
- `pnpm run deploy` → `wrangler deploy --minify`
- `pnpm run cf-typegen` → run after editing `wrangler.jsonc` bindings.
- `pnpm run db:generate` → `drizzle-kit generate`, writes a new SQL migration.
- `pnpm run db:migrate:local` / `pnpm run db:migrate:remote` → apply migrations with Wrangler.
- `pnpm run keys:generate` → prints a fresh Ed25519 keypair for `JWT_PRIVATE_KEY`.
- `pnpm run admin:bootstrap [-- --remote]` → asks for an address and seeds the first admin.
- `pnpm run applications -- <list|show|create|update|rotate-secret|revoke-secret|delete> [--remote]`
  → configures client applications and their secrets straight in D1; `-- --help` prints the full
  flag list.

## Environment

`.dev.vars` (gitignored, copy from `.dev.vars.example`) holds the secrets:
`JWT_PRIVATE_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, plus local overrides of
`AUTH_PUBLIC_URL` / `AUTH_ISSUER`. Non-secret config (`AUTH_PUBLIC_URL`, `AUTH_ISSUER`,
`MAIL_FROM_*`) lives in `wrangler.jsonc` under `vars`. `AUTH_LOGIN_URL` names the sign-in
front-end `/oauth/authorize` hands the browser to; it is set in `wrangler.jsonc` and falls back to
`DEFAULT_LOGIN_URL` in `lib/config.ts`. There is no in-Worker page to fall back to.

## Source layout

- `src/index.ts` — Hono app: CORS/charset/cache middleware, `onError`, `GET /`, route mounting,
  `/openapi.json`.
- `src/db/schema.ts` — the entire D1 schema. `src/db/client.ts` builds a per-request Drizzle
  client.
- `src/lib/` — `crypto.ts` (tokens, hashing, constant-time compare), `jwt.ts` (EdDSA signing,
  access and ID tokens, JWKS), `pkce.ts`, `errors.ts` (`OAuthException`), `config.ts` (TTLs,
  grants, client authentication methods, `DEFAULT_LOGIN_URL`).
- `src/providers/` — `types.ts` defines `ProviderProfile` / `AuthorizationRequest`;
  `magic-link.ts` and `google.ts` implement them; `index.ts` is the registry.
- `src/services/` — `applications.ts` (clients, redirect URIs, scopes, secrets, client
  authentication), `authorization-requests.ts` (requests parked at `/oauth/authorize`),
  `users.ts` (account resolution, roles), `tokens.ts` (codes, sessions, refresh rotation, the
  token responses), `invitations.ts`, `email.ts`, `audit.ts`, `authorization.ts` (the shared flow
  head and tail).
- `src/routes/` — one file per area (`authorize`, `token`, `userinfo`, `introspect`, `logout`,
  `google`, `magic-link`, `me`, `well-known`); `routes/admin/` is the permission-gated admin API.
- `src/middleware/auth.ts` — `requireAuth` and `requirePermission`. `src/middleware/cors.ts` —
  cross-origin access driven by the registered clients.
- `migrations/` — `0000_init.sql` and `0003`/`0004` generated by drizzle-kit, `0001_seed.sql`,
  `0002_cms_application.sql` and `0005_repair_client_config.sql` hand-written.

## Architecture notes (non-obvious)

- **This Worker renders no HTML at all.** It answers JSON and redirects, nothing else — the whole
  monorepo behind `api.franciscosolis.cl` is a backend. The one step of an OAuth flow that has to
  put something in front of a human is delegated: `GET /oauth/authorize` parks the request and
  redirects to the sign-in front-end (`AUTH_LOGIN_URL`, defaulting to `DEFAULT_LOGIN_URL` =
  `https://franciscosolis.cl/apps/auth`) with `?request=<handle>`. A value that does not parse as a
  URL falls back to the default rather than failing, because there is no page here to fail over to.
  Do not reintroduce a `c.html()` anywhere in this Worker.
- **One authorization endpoint, and two older ones that still work**: `GET /oauth/authorize` is
  the entry point a relying party discovers. It validates the request once, parks it in
  `authorization_requests`, and sends the browser to the sign-in front-end; the provider the user
  picks there resumes that row. `POST /magic-link` and `GET /oauth/google/authorize` take the same
  parameters and remain the direct route in — the parked request is a place to *hold* a validated
  request, not a new protocol. Both entries into Google go through `startGoogleFlow`, so they
  cannot drift.
- **The parked request is deliberately not single-use**, unlike every other one-time token here. A
  user who mistypes their address or changes their mind about the provider has to be able to come
  back to it. Holding it grants nothing: a provider still has to authenticate someone, and the code
  still goes to the client's registered redirect URI. Its expiry is the whole limit.
- **A client's secrets are rows, not a column**: `application_secrets` holds several live secrets
  per client, which is what makes a rotation overlap instead of cutting the old value off. The
  token endpoint checks the presented secret against every one currently alive and stamps
  `last_used_at` on the match. Rotation sets an `expires_at` on the others rather than revoking
  them; a grace of 0 revokes, which is the leaked-secret case. Never reintroduce a single
  `client_secret_hash` column — the overlap is the feature.
- **PKCE is mandatory, with exactly one escape hatch**: a *confidential* client may set
  `require_pkce = false`, because its secret is the binding PKCE would otherwise provide. A public
  client can never opt out, and `resolvePkceRule` heals the invariant rather than storing a client
  that breaks it. A code minted *with* a challenge always has to be answered with a verifier, even
  if the client's flag changed in between — turning the flag off must not unbind a live code.
- **`id_token` is issued only for `openid`**, carries `nonce` and `at_hash` from the request it
  belongs to, and takes `auth_time` from the session rather than from the exchange, so refreshing
  never makes an old authentication look fresh. A refresh deliberately does not replay the nonce.
  `groups` duplicates `roles` because relying parties doing group-based access control read that
  name — Cloudflare Access is the reason it exists.
- **CORS is decided from the database, in this Worker**: the gateway's fixed origin allowlist
  cannot describe clients that live on their own domains, so `apps/api` skips its CORS middleware
  for `/auth/*` (`ownsCors` in its service registry) and `src/middleware/cors.ts` answers instead,
  allowing any origin a registered active client redirects to or lists in `allowed_origins`.
  Credentials are never allowed: nothing here authenticates with a cookie. The split that decides
  *which* paths answer at all is `fetch` versus navigation, not public versus private: `GET /`,
  `/me/*`, `/logout` and the whole admin API are on the list because a front-end calls them with
  `fetch`, while `/oauth/authorize` and the two provider callbacks are off it because the browser
  navigates to them and their answer is a redirect carrying a one-time code. Opening the admin API
  costs nothing — every route behind it still needs a bearer token and a permission, and no request
  here carries ambient authority for an origin to abuse. `GET /oauth/authorize/:handle` and its
  `/magic-link` sibling are matched by `CORS_PARKED_REQUEST` rather than by a subtree, because the
  sign-in front-end reads and posts to them with `fetch` from another origin while their third
  sibling, `/oauth/authorize/:handle/google`, is a navigation and must stay off the list.
- **A client credentials token has no `sid`**, because no one was authenticated. `requireAuth`
  refuses it outright rather than letting it through with an empty permission set, so every route
  that acts on behalf of a user stays user-only.
- **Providers converge, they do not branch**: every provider's only job is producing a
  verified `ProviderProfile`. Everything after that — account resolution, authorization
  code, redirect — lives in `completeAuthentication` (`src/services/authorization.ts`).
  A new provider is a `ProviderDescriptor` + a routes file, nothing else.
- **`emailVerified` is load-bearing**: `resolveUserForProfile` links a provider identity to
  an existing account by email address. That is only safe because the profile is required
  to be verified; dropping the check would let a new provider claim someone's account.
- **Two error shapes on purpose**: `/oauth/*` answers RFC 6749's `{ error, error_description }`
  (via `OAuthException`), everything else uses this monorepo's `{ code, error }`. `onError`
  in `src/index.ts` picks by error type — don't collapse them.
- **Token endpoint is not enveloped**: `POST /oauth/token` returns the flat OAuth token
  response, not `{ code, data }`, so off-the-shelf OAuth clients work. Same for `/oauth/revoke`.
- **One-time tokens are compare-and-swap**: magic link tokens, authorization codes, OAuth
  states and refresh tokens are all consumed with `UPDATE ... WHERE consumed_at IS NULL
  RETURNING id` and treated as spent when zero rows come back. That, not a prior SELECT, is
  what makes them single-use under concurrency. Keep the pattern for any new one-time token.
- **Refresh reuse revokes the session, not just the token** (`consumeRefreshToken`): replaying
  a rotated token means it leaked, so the whole chain dies. This is intentional and will log
  out the legitimate user too.
- **Roles are re-read per request**, never trusted from the token body (`requireAuth`), so a
  revoked role or a revoked session takes effect immediately instead of at token expiry. The
  claims in the token are for consumers that verify offline.
- **Guards check permissions, not roles** (`requirePermission('users:write')`), so roles stay
  freely re-definable through the admin API.
- **Only the hash of anything user-facing is stored** — tokens, codes, invitations, client
  secrets. A database dump must not be enough to impersonate anyone.
- **`AUTH_PUBLIC_URL` is not derivable from the request**: behind the service binding the
  incoming URL is internal, so magic links and the Google `redirect_uri` are built from this
  var. Getting it wrong silently breaks both flows.
- **Sign-up is invitation-only, with no environment bypass**: an unknown address is refused
  unless it has a pending invitation. `POST /magic-link` still answers 202 either way — do
  not make it leak which addresses exist. The first admin is not a special case in the code:
  `scripts/bootstrap-admin.mjs` writes an ordinary invitation carrying the `admin` role
  straight into D1, so the sign-up path stays single. Do not reintroduce an env-var allowlist.
- **Client applications are configurable without a token**: `scripts/configure-applications.mjs`
  writes to D1 through Wrangler, because the admin API needs `applications:write`, which nobody has
  until a client exists to sign in through. It mirrors the admin routes deliberately — same
  validation, same base64url secret hashed with SHA-256, same grace-period semantics, same audit
  events — and additionally covers deletion, which the API intentionally does not expose
  (`application.deleted` in `AuditEvent` exists only for it). Values are interpolated into SQL, so
  anything with control characters is refused rather than escaped. When changing secret handling,
  change both: they are two implementations of one policy.
- **Email bodies live in `@franciscosolis/emails`, and rendering is async.** `services/email.ts`
  is now a thin wrapper: `magicLinkTemplate` and `invitationTemplate` return *promises* of
  `{ subject, html, text }`, so every call site awaits them. There is no `escapeHtml` here any
  more — react-email escapes children — and no hand-written plain-text twin, because the text
  part is derived from the rendered HTML. Add a new email as a template in that package, not as
  a string in this Worker.
- **Prettier is aliased out of the bundle** (`alias` in `wrangler.jsonc`, mirrored in
  `vitest.config.ts`): `@react-email/render` imports it statically for a `pretty: true` option
  this Worker never uses, and it is ~1.5 MB of formatter parsed on every cold start. The stub
  (`packages/emails/src/prettier-stub.ts`) throws if it is ever actually called.
- **The seed migration is hand-written and idempotent**: `0001_seed.sql` is not in drizzle's
  `meta/_journal.json` because it contains no DDL. Adding DDL there would desynchronise the
  drizzle snapshot — put schema changes in a generated migration instead. `0002` and `0005` follow
  the same rule.
- **The client applications are repaired by a migration, not only registered by one**:
  `0005_repair_client_config.sql` refills `grant_types` where it is empty and adds the redirect
  URIs the front-end actually calls back to. An empty `grant_types` makes the token endpoint answer
  `unauthorized_client` for every grant, and it is not a state the admin API can write, so it is
  healed rather than left to surface at sign-in. Both halves only ever add — a client narrowed on
  purpose keeps its grants, and an existing redirect URI is not duplicated — so re-applying it is a
  no-op. Where the front-end serves its callbacks is therefore part of this Worker's configuration:
  moving `/auth/callback` or `/apps/cms/callback` in `franciscosolis.cl` means registering the new
  URI here first, and `test/functional/seeded-clients.test.ts` is what holds the two in step.
- **Two generated migrations carry hand edits, both flagged in a header comment.** `drizzle-kit`
  numbers files from the journal, which the hand-written 0001/0002 are absent from, so a generated
  file has to be renumbered past them (rename the file, then set `idx`/`tag` on the last journal
  entry — `idx + 1` is what the next generation is named from). And the generator emits DDL only:
  0003 needed its `INSERT ... SELECT` corrected where a rebuilt table also gained a column, and
  0004 needed the data move written by hand *before* the `DROP COLUMN` it generated. Read those
  headers before regenerating anything.
- **There is no session of this server's own.** Every sign-in goes out to a provider, so
  `prompt=none` is answered with `login_required` and RP-initiated logout ends the session here
  without ending the one at Google. Adding SSO would mean adding a cookie on
  `api.franciscosolis.cl`, which is a deliberate non-goal so far.
